## Item 1: show admitted XMD inside its Evaluate enclosure

The execution reading lets a person follow the generated program where its
producer ran. The older corrected reference keeps Evaluate's opening and closing
tags visible and replaces the inner Plan content with the admitted program.

Today, the REPL's entry-wide transcript describes admission as an event and
appends generated source. Core already retains the admitted program and the
producing Evaluate position. That position identifies the enclosing Evaluate;
it does not identify a particular producer child as the sole source of the text.

**Accepted behavior.** For a paired Evaluate, show its original content before admission.
Once the selected retained prefix contains a successful admission, replace its
inner producer content in the display with the exact admitted source. Keep the
Evaluate opening/closing tags and enclosing source rail. Generated executable
children belong beneath that enclosure. This is a display projection of retained
facts, with live badges supplied separately by session middleware.

For the packet's [plan-entry.md](plan-entry.md), the reading initially shows
Evaluate containing Plan and its prompt. After admission it shows Evaluate
containing the program beginning `# Create a project README` from
[generated-readme.md](generated-readme.md). The program is XMD source; its rendered
result has a separate output role.

Preserve the original submitted source and Journal bytes. An earlier inspected
prefix still shows the producer content and contains no future generated source
or live badges. Returning live shows the latest admitted reading. Inspection
does not run the producer or fragment.

Admit replacement only when the retained owner and producing position identify
the enclosing source span unambiguously. Do not guess a Plan by name, attach a
fragment to a sibling, replace several separate producer children independently,
or fabricate syntax that was not submitted. A refusal is not a successful
replacement. Missing/ambiguous source ownership follows the existing refusal
contract.

**Proposed product verification.** Run the original Plan journey to admission,
then inspect a prefix from before admission and return live. After admission,
the generated heading and first Elicit occupy the producer content's place
inside Evaluate. Before admission, Plan and its original prompt remain there.
Generated source and rendered output remain visually distinct. The source and
Journal remain byte-identical during inspection, with no provider activity.
Appending the program below an unchanged producer as an unrelated transcript
event does not satisfy this behavior.

**Decision: accepted.** The Product Owner accepts preserving Evaluate's enclosure
and replacing its inner producer content with the admitted program. Original
source remains unchanged; an earlier checkpoint shows the producer again;
rendered output remains separate. This is a feature decision, not a reusable rule.

## Item 2: show the program owned by a self-closing Evaluate

The existing self-closing form takes a program from a value:

```md
<Evaluate text={program} allow={["read"]} />
```

It has no inner producer content to replace. Keeping its authored row visible
preserves both that input form and the expression supplying the program. The
older reference's paired example does not settle this display adaptation.

**Accepted behavior.** After successful admission, preserve the self-closing row and
display its exact admitted program directly beneath it as a generated child
source region. Connect that child to Evaluate's source rail. Do not manufacture
an opening/closing pair or place the generated source in the rendered-output
role. For a program reading notes.md, the source reading is:

```text
<Evaluate text={program} allow={["read"]} />
  │ <File path="notes.md" />
```

This example illustrates ownership and reading order; measured placement and
rail styling are reviewed separately. The generated bytes retain their own
identity and source offsets. Visual indentation and rails are decorations,
not changes to the submitted or admitted source.

Before admission, or when inspecting an earlier prefix, show the authored row
without a future generated child. A refused admission does not acquire a
successful generated child. Use the same unambiguous retained-owner requirement
as item 1. Inspection reads retained facts without executing the program.

**Proposed product verification.** Submit a self-closing Evaluate whose program
reads notes.md. After admission, its authored `text={program}` row remains and
the admitted File source appears directly beneath it. The note's contents occupy
the separate rendered-output role. Inspect before admission and return live:
the child appears only in prefixes containing that admission. Fabricated paired
syntax, unrelated appended source, and displaying the note as generated XMD
each fail this behavior.

**Decision: accepted.** The Product Owner accepts keeping the self-closing
Evaluate row and attaching its admitted program directly beneath it as generated
source. Rendered output stays separate; earlier prefixes omit the future child.

## Item 3: reach all source and rendered text at every supported width

The long schema in [generated-readme.md](generated-readme.md) must remain
readable at 72×20, as must a long README preview. Existing drawer and list
windows already reach content through measured capacity and earlier/later
controls. The main transcript currently splits explicit newlines into rows;
it has no equivalent source-reading window. PR 1 bounds visible text runs and
preserves their colours, but deliberately leaves this reading policy unchanged.

**Accepted behavior.** Soft-wrap authored/generated source and rendered output to the
available measured content width. Preserve every source character, token role,
explicit newline and blank line in the logical reading. A visual wrap inserts no
newline into source, bindings or Journal data. Ordinary word boundaries are
preferred; a token longer than the row still continues across rows so its tail
remains reachable. Continuations stay attached to the same source owner and
rail, and acquire no extra lifecycle badge or executable occurrence.

Use the established vertical window pattern for the main source/output reading:
`[↑ earlier]` and `[↓ later]` remain outside the moving content. Every wrapped
row is reachable. Decoration and controls consume measured capacity before
admission; nothing spills into another pane or the fixed seven-row footer.
Source previews use the same text policy inside their existing drawer window.
This proposal adds no horizontal scrolling interaction. Editable fields and the
persistent single-row draft retain their existing behavior.

Keep window positions private to the process and the selected reading, following
the existing scope/prefix ownership pattern. Scrolling changes no selection,
answer, permission, location or Journal. A resize remeasures wrapping and window
capacity, clamps the position, and preserves selection/focus through the existing
admission rules. Rows outside the window contribute no nodes or targets.

The engine supplies text fit and geometry; do not infer cell width from string
length or create another screen-coordinate calculator. The installed text
operations expose wrapping, while the current REPL measurement adapter returns
box bounds rather than a public line-break map. The Planner derives the smallest
private measurement adaptation needed for row windows, preserving the existing
renderer ownership and measured-frame boundary. No dependency change is implied.

Metadata labels keep their established shortening rules. Source and rendered
content use continuation rows rather than an ellipsis that hides their tail.
Output owner and section placement remain item 5; this item settles text access.

**Proposed product verification.** Read the original generated schema and README
preview at 160×36, 120×30 and 72×20. Use earlier/later to reach the schema's closing
delimiters and the preview's last line. Include an unbroken value wider than the
pane and a line with non-ASCII text, so character counting cannot stand in for
measured fit. Resize while reading, then inspect an earlier prefix and return
live. All selected content remains reachable, decorations and controls stay in
their measured regions, and source/Journal bytes and execution remain unchanged.
Preserving colour only on a clipped prefix, overflowing a neighboring pane,
or making the last row unreachable each fails this behavior.

**Decision: accepted with revised labels.** The Product Owner accepts soft
wrapping and vertical window controls, and replaces the confusing `^`/`v`
characters with `↑`/`↓`. Use `[↑ earlier]` and `[↓ later]` consistently for the
new reading and existing Sessions, Entries and drawer window controls. Retain
their semantic actions and normal activation behavior; the arrows are labels,
not new keyboard bindings. Measure the complete Unicode labels and verify their
rendering and hit targets. This presentation change belongs to PR 2; PR 1's
accepted commit and evidence remain historical records of its frozen slice.

## Item 4: connect nested source with rails and readable lifecycle badges

The older reference places lifecycle glyphs beside source and joins paired
elements with nested vertical rails. Its phase labels sit in a separate fixed
screen column. The terminal must preserve those relationships when that column
has no room, especially after source begins wrapping.

Keep one source rail per displayed enclosing element, connecting
its opening and closing source positions. Nested source receives nested rails;
continuation rows carry the same enclosure. Generated source inherits its
Evaluate enclosure under items 1 and 2. Rails describe source structure even
when that source has no live invocation observation.

**Accepted placement:** reserve one measured status
column at the right edge of the source pane. Put the current glyph and full
state word there on the first visual row of its element. Align statuses across
nesting levels. The left side carries source rails and token-coloured source.

Measure the column for the longest supported status reading, including a cleanup
wait, and keep that reservation stable as phases change. Measure the separation
from source as part of the row. Long source wraps within the remaining content
width; its badge stays on the first visual row. Continuations keep their source
rails and leave the status column blank. No separate status-only row is needed
at the supported profiles. Paired closing EXIT/terminal markers, when actually
observed, use the same right-hand column. No phase glyph remains in the left
source gutter. A wrapped line does not acquire a second invocation or badge.

For example, with source attributes abbreviated only in this illustration:

```text
│ <Evaluate …>                  ● ACTIVE
│ │ <Plan>                      ● ACTIVE
│ │ │ <Elicit …>                ● WAITING
```

The column ends at the pane's measured inner edge, not the terminal's edge or
another pane. A word remains complete at 72×20; source gains continuation rows
instead of losing characters. Do not shorten WAITING to an unexplained glyph,
elide source to retain the badge, or paint a label over another region.

Use the older reference's lifecycle colours with their glyphs and state words:

| Reading | Glyph | Colour |
| --- | --- | --- |
| ENTER | ▶ | `#5aa87c` |
| ACTIVE | ● | `#7fd3e8` |
| WAITING | ● | `#c99a3f` |
| EXIT | ◀ | `#c2766e` |
| SETTLED | ✓ | `#4f8468` |
| FAILED | × | `#d24b3f` |

Cancellation keeps the accepted textual cancelled reading. A wait during cleanup
keeps EXIT visible alongside WAITING, rather than implying the body resumed.
Repeated or concurrent calls receive separate private occurrence readings within
their owned source group; a source id alone cannot combine their badges.
Unselected source has rails without a fabricated execution state. Historical
inspection has source rails but no live badges; return live restores the latest
session reading. No minimum frame duration or execution delay is introduced.

**Proposed product verification.** In the original nested journey, identify
Evaluate, Plan and the actual pending Elicit from their own rails and badges.
Hold cleanup and observe EXIT until final acceptance. At all supported profiles,
the full state words align at the source pane's right edge. At 72×20, reach
wrapped source through the window without losing characters; the first visual
row carries the badge and continuation rows leave its column blank. Transition
from ACTIVE to WAITING to terminal state without changing the reserved column
or rewrapping source solely because the state word changed.
Inspect an earlier prefix while execution advances: its source rails remain,
its live badges disappear, and returning live restores the latest state.
Include two real calls sharing a logical source id so one cannot overwrite the
other. A single entry-level progress badge, colour without a state word,
duplicated continuation badges or historical live-state leakage fails.

**Decision: accepted.** The Product Owner confirms a shared right-aligned status
column at the end of the line. All phase glyphs and words use it; nesting rails
stay on the left. Long source wraps in the remaining width, with the badge on
its first visual row and a stable reservation across state changes.

## Item 5: read rendered output before the entry's source

The original reference gives the settled entry's rendered document visual
priority. Its generated source is a separate execution reading. The current
flat transcript interleaves source/admission/effect summaries before the entry's
final result, so the useful result can be buried below machinery.

The session already receives an entry-owned output stream. The selected entry's
retained root close supplies its final rendered output and outcome. Evaluated
blocks can also retain output with their actual source-region owner. These are
different facts: a retained block output does not prove that its parent emitted
the same text to the entry, and lifecycle `Result<void>` carries no rendered
value. No general per-component rendered-output record exists in this contract.

**Accepted behavior.** When reading an entry, put an `Output` section before its `Source`
section within the existing transcript pane. The Output section contains the
actual entry-rendered text. The Source section contains the accepted authored/
generated projection and rails. Both belong to the selected entry and share its
measured vertical reading window. These sections create no additional pane or
route. Source remains reachable through `[↑ earlier]` / `[↓ later]`.

The output starts at the entry's first reading position; do not automatically
move a window already being read when output arrives. For the original packet
journey, the Output section begins with the rendered `Create a project README`
heading and includes the actual preview and `README.md was created.` text.
The Source section shows the admitted Evaluate program separately. Do not
synthesize a write receipt, interpret a bound value as output, or print the
generated program itself in the Output section.

While an entry runs, show the session's emitted text with the label
`Output · live`. Once the retained final result exists, its text replaces the
live reading exactly once and the heading becomes `Output`. The retained result
wins even if it differs from a partial live stream. A retained empty result
shows `No rendered output.` alongside the actual entry outcome. If an inspected
prefix has no entry-rendered output record, say
`No entry output recorded at this checkpoint.` rather than borrowing live or
later output. Keep existing failure/cancellation diagnostics and truthful entry
outcomes visible; text containing the word "failed" does not decide an outcome.

Reading a nested source scope remains a source reading. Display a retained
block's output at its recorded owner as `Recorded block output` when available;
do not label the entry's entire final result as that component's output or
assemble local block outputs into a fabricated entry result. Agent response
text remains in its Agent reading, and a binding remains in its binding reading.
If the existing records cannot establish a narrower owner, display the output
only at its known entry owner. No middleware payload or persistence extension
is required for these section relationships.

**Proposed product verification.** Run the original Plan journey and open the
settled entry. Its rendered heading, preview and final report appear in the
Output section before Source, without an intervening list of effect summaries.
At each supported profile, the first reading window begins with rendered text
and earlier/later reaches the final report and source. Read a nested generated
scope: source remains that scope's, and entry output is not attributed to its
Elicit or File. Include a bound value that renders nothing and a printed word
"failed" in a successful entry. Inspect before the root close and cold reopen
afterward: no future output, live overlay, duplicate result or provider call
appears. An entry-wide dump below unrelated events or synthesized output fails.

**Decision: accepted.** The Product Owner accepts Output before Source for the
entry reading. Live output is explicitly labelled and replaced by the retained
final result; earlier checkpoints contain only their retained facts. Nested
source readings receive output only where its narrower owner is known.
