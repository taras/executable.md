## Observable delivery

In an existing ambient checkout, an executing entry records:

- Authored paired `<File path="…">…</File>` writes after content expansion.
- Authored self-closing `<File.Delete path="…" />` deletions.
- Authored paired `<Dir path="…">…</Dir>` directory ensures before entering their content.
- Captured generated File writes/deletes admitted by the existing REPL evaluation tables and permission ceiling.

A completed operation returns its saved composed Result during continuation without calling ordinary middleware, live path canonicalization, checkout discovery, a lease or a native mutation. A later operation invokes the live provider. Changed/deleted checkout contents do not invalidate a completed result. Existing lexical form/path checks and permissions still apply; those checks are not checkout validation.

Keep outside-checkout mutations ordinary and unrecorded as local repository mutations. Keep File reads, Globs, temporary directories and other operations ordinary. Node/Bun REPL File/Dir and all ordinary-run/workflow behavior remain intact. An entry that does no relevant mutation acquires no repository resource.

### Example

Type this complete entry in a Deno or compiled REPL started inside a seeded checkout:

```xmd
<Dir path="drafts">
<File path="note.md">first</File>
<File path="obsolete.md">remove me</File>
<File.Delete path="obsolete.md" />
</Dir>
<Elicit schema={{ type: "object", properties: { decision: { type: "string", enum: ["continue"] } }, required: ["decision"], additionalProperties: false }} as="answer">Continue this experiment?</Elicit>
<File path="after.md">continued</File>
```

Before answering, `drafts/note.md` contains `first`, `drafts/obsolete.md` is absent and `after.md` is absent. Leave through `[exit]` with the question still waiting. Change `drafts/note.md` externally and recreate `drafts/obsolete.md`. Reopen the printed location at the live head: the question is offered again, both external changes remain, and no completed File/Dir operation runs again. Answer through the real drawer: the new `after.md` write executes. A frozen location displays only history and calls no repository setup.

An entry's local success says what its Files provider answered. It proves neither current disk contents nor external publication.

## Accepted scoped setup contract

Use ordinary setup functions, not a contextual installation operation. Add neither `Repository.install()` nor a separate `RepositoryInstaller`, `RepositoryProvider` or `RepositorySetup` API. Existing `Repository.around()`, `Git.around()` and `Files.around()` install the execution behavior. Setup itself needs no middleware seam or public API export.

Each selected setup takes `readonly ExecutionInstallation[]` and returns `Operation<readonly ExecutionInstallation[]>`. Call it inside the existing executing run or entry scope, before `executeInstalled()`, and pass the prepared installations to that unchanged core boundary. Each call creates fresh state in local variables. There is no execution id, entry key, command-kind field, source/site parameter or separate generated `files` result. Selection of the setup follows the command already parsed; do not infer mode from a journal.

The existing REPL entry task supplies the scope. Call setup after `agent.owning(key)` and after the running-slot finalizers are registered, before canonical execution. Setup creates no checkout, performs no discovery or mutation and acquires no lease. Its middleware and later lazy resources belong to that scope. Execution and native work stop and join before resources release and the slot becomes available. No extra lifecycle protocol, nested execution scope or per-entry factory API is needed.

Ordinary setup installs existing `useRunComposition` behavior and returns its input installations unchanged. REPL setup prepares authored mutation recording and wraps each existing captured `evaluation.files` access in the returned installations. Preserve every other installation member and the command's permission tables. An installation without captured access gains none. Do not replace supplied access with a new ambient `ordinaryFragmentFiles()` instance. Missing access keeps its existing refusal; generated Dir remains excluded.

A host with no repository setup passes the original installations unchanged and creates no recorder or resources. File/Dir still require the ordinary Files provider; this behavior supplies no native fallback. Repository/Git operations keep their existing missing-provider errors. Node/Bun load no Deno repository graph.

An isolated `host="run"` child calls ordinary setup in its own execution scope, after its cwd and host Files assembly. It receives no parent recorder, selection memo, lease or publication state. A child of `xmd test` still gets ordinary run behavior although that command installs no operational repository provider for itself. Passive history never calls entry setup.
