# Deterministic agent tests

`@executablemd/test-agent` replaces a coding agent with a scripted ACP agent.
Your test still crosses ACPX, sessions, prompts, and provider teardown, but
the response is declared in Markdown instead of generated by a model. That
makes integration tests fast to understand and repeatable to run.

For running a real ACP-compatible agent from a document, start with the
[coding-agent guide](https://executable.md/docs/agents).

## Try the test agent through ACPX

This path is useful when you want to inspect the ACP boundary directly. The
scenario is the agent's script: each stage matches one incoming prompt, then
the Markdown before the next stage is the reply.

Create `examples/review.md`:

```md
<WhenPrompt
  as="review"
  template="Review {?subject} at revision {?revision}"
/>

The review of **{review.subject}** at `{review.revision}` passed.

<WhenPrompt template="Summarize {review.subject}" />

The review of **{review.subject}** passed.
```

Start the walkthrough controller from this checkout:

```sh
deno run --allow-all packages/test-agent/examples/acpx-walkthrough.ts
```

It prints two complete `acpx` commands. Run those commands in a second
terminal, in order. They send the two prompts above through ACPX and print the
two scripted replies.

The controller creates the connection route and keeps the scenario state. The
worker command, `xmd test-agent --connect <route>`, only works while that
controller is running; it does not accept a scenario file directly. After a
released `xmd` is on your `PATH`, the printed agent command has this shape:

```sh
acpx --agent "xmd test-agent --connect <route>" exec "Review packages/core at revision abc123"
acpx --agent "xmd test-agent --connect <route>" exec "Summarize packages/core"
```

Each `acpx exec` starts a temporary ACP session. The second reply can still use
the first prompt's capture because the controller journals completed scenario
stages and supplies that state to a fresh worker.

## Use it in an Executable Markdown test

Most projects use the test agent through `xmd test`. Keep the test document and
the scenario in separate files: the first describes the application behavior;
the second describes the controlled agent behavior.

`tests/agent-integration.md` establishes the controller scope, maps an agent
and session to the scenario, then uses the ordinary agent components:

```md
<TestAgent>
  <TestAgent.Scenario
    agent="test"
    session="review"
    src="./agents/review.md"
  />

  <Test name="reviews a change">
    <Agent name="test">
      <Session name="review">
        <Prompt prompt="Review packages/core at revision abc123" as="firstReply" />
        <Prompt prompt="Summarize packages/core" as="secondReply" />
      </Session>
    </Agent>
    <AssertStringIncludes actual={firstReply} expected="The review of **packages/core** at `abc123` passed." />
    <AssertStringIncludes actual={secondReply} expected="The review of **packages/core** passed." />
  </Test>
</TestAgent>
```

`tests/agents/review.md` is the scenario shown in the direct walkthrough
above. Run the test as usual:

```sh
xmd test tests/agent-integration.md
```

`<TestAgent>` is valid inside an active `xmd test` session. It starts its
controller lazily and tears it down with its scope, including ACPX and worker
resources. `xmd test` intentionally rejects the `xmd run` agent flags because
this controlled stack supplies the provider.

## Write scenarios

`<TestAgent>` establishes the controller and configuration scope.
`<TestAgent.Scenario>` maps one agent and logical session to a scenario
document. The mapping has this shape:

```text
(agent, logical session) → scenario document
```

When `agent` is omitted on `<TestAgent>`, its default agent is `test`. A
scenario without `agent` inherits that resolved default. An omitted `session`
maps only the unnamed default session; it is not a wildcard for named sessions.

`<WhenPrompt>` is a matcher, not an outgoing prompt. It matches the entire
incoming prompt. Text after a successful matcher is the response; the next
`<WhenPrompt>` begins the next stage. `{?name}` captures text, and `as` stores
those captures in scenario state. Later stages reuse them with `{binding}`:

```md
<WhenPrompt as="change" template="Review {?path}" />

Reviewed {change.path}.

<WhenPrompt template="Summarize {change.path}" />

The summary is ready.
```

The first stage exposes `change.path` to the second. A literal in a template is
a constraint, so accidental prompt changes fail the test rather than being
silently accepted.

Each resolved ACP session receives its own scenario document and journal. The
same mapping key therefore does not leak state across `<Test>` blocks, and a
different contextual working directory receives a separate scenario instance.
It is fine for a test to end while a scenario waits at a later stage; unused
stages do not fail teardown.

## Failures you can act on

Missing or duplicate scenario mappings fail the owning test before an agent
turn starts. A malformed scenario, unsupported dependency, or invalid setup
also fails the test instead of leaving a downstream assertion to diagnose it.

When a prompt does not match, the test fails the owning turn and reports both
the expected template and the actual prompt. Compare those two strings first:
they usually reveal a changed prompt, missing capture, wrong agent, wrong
session, or a stage that has already been consumed. A prompt after the last
stage reports `scenario exhausted`.

Scenarios deliberately keep the surface small: they provide ordered whole-prompt
matching, captured values, Markdown components, and controlled scenario files.
They do not provide regular expressions, ignored intermediate prompts, response
event scripting, or access to the shared workspace. This keeps an integration
test focused on the behavior it means to prove.
